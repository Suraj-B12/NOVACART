Why CouchDB?

          

            

              
{ }

              
Document-Oriented

              
Stores data as JSON documents with flexible schemas. A smartphone and a book can live in the same collection with completely different fields — no migrations needed.

            

            

              
GET

              
Built-in REST API

              
Every operation is an HTTP request. No drivers or ORMs needed — any language with HTTP support can talk to CouchDB directly from the browser.

            

            

              
M/R

              
MapReduce Views

              
Pre-computed indexes using JavaScript map/reduce functions. Category stats, revenue aggregations, and stock alerts are computed once and cached by CouchDB.

            

            

              
?

              
Mango Queries

              
MongoDB-style JSON query language via the _find endpoint. Supports selectors like $gte, $regex, and $lte with automatic index selection.

            

            

              
MVCC

              
Revision Control

              
Every document update creates a new revision (_rev). No data is ever overwritten — CouchDB uses Multi-Version Concurrency Control for conflict-free writes.

            

            

              
SYNC

              
Replication

              
Master-master replication built into the core. Databases can sync bidirectionally across servers, enabling offline-first apps and distributed architectures.

            

          

        


        
        

          
Quick Reference

          

            

              
Document Structure +

              

                
All data stored as JSON documents in one database. A type field distinguishes them:

                
// Product document
{
  "type": "product",
  "name": "iPhone 16 Pro",
  "category": "Electronics",
  "subcategory": "Smartphones",
  "price": 134900,
  "currency": "INR",
  "rating": 4.9,
  "stock": 45,
  "specs": { "Display": "6.3 inch",
             "Chip": "A18 Pro" },
  "tags": ["new", "bestseller"]
}

                
No fixed schema. A book has specs.Pages, a phone has specs.RAM — same collection, different shapes.

              

            

            

              
How couchFetch() Works +

              

                
async function couchFetch(path, options) {
  // 1. Add auth + JSON headers
  // 2. Measure response time
  const res = await fetch(DB_URL + path, {
    headers: {
      'Authorization': 'Basic ...',
      'Content-Type': 'application/json'
    }
  });
  // 3. Log to CouchDB (shared log)
  // 4. Return parsed JSON
  return res.json();
}

                
Every CouchDB operation is a standard HTTP request. No drivers, no ORM — just fetch().

              

            

            

              
MapReduce vs Mango +

              

                
MapReduce Views — Pre-computed indexes using JS functions. Best for known query patterns and aggregations (category stats, revenue totals). Indexed at write time.

                
Mango Queries — MongoDB-style JSON selectors via POST /_find. Best for ad-hoc filtering (user search, price range, rating filter). Evaluated at query time.

                
NovaCart uses 8 MapReduce views for analytics and 4 Mango indexes for product search.

              

            

            

              
CouchDB vs SQL Comparison +

              

                
SQL:     SELECT * FROM products
              WHERE category = 'Electronics'
              AND price BETWEEN 20000 AND 50000

CouchDB: POST /_find
         { "selector": {
             "type": "product",
             "category": "Electronics",
             "price": {"$gte":20000, "$lte":50000}
         }}

SQL:     SELECT category, AVG(price)
              FROM products GROUP BY category

CouchDB: GET /_design/catalog/
              _view/category_stats?group=true
         (uses MapReduce with custom reduce)

              

            

            

              
MVCC & Revisions +

              

                
Every document has a _rev field (e.g., "3-a1b2c3"). Format: {generation}-{hash}.

                
POST /db         → _rev: "1-abc"  (created)
PUT  /db/id      → _rev: "2-def"  (updated)
PUT  /db/id      → _rev: "3-ghi"  (updated)
PUT  with rev 1  → 409 Conflict!  (stale)

                
Optimistic concurrency — no locks. First writer wins, second must re-read and retry. Old revisions kept until compaction.

              

            

            

              
HTTP Methods in CouchDB +

              

                
GET — Read data. Safe, idempotent. Used for views and document retrieval.

                
POST — Create document (auto-ID) or execute query (_find, _index). Not idempotent.

                
PUT — Create/update at specific URL. Requires _rev for updates. Idempotent.

                
DELETE — Soft delete — adds _deleted: true. Revision history preserved.
